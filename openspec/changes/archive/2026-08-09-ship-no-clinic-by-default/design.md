## Context

See `proposal.md` § *Why*. What shapes the approach is that most of the machinery already exists and
points the right way — the change is mostly subtraction.

Measured on the current tree:

- `require_site()` in `scripts/env.sh` already refuses on an unset `SITE` and on a `SITE` that names
  a directory with no `site.sh`, printing the `deis.py` commands both times. Removing the shipped
  establishment removes the *shortcut*, not a code path that has to be built.
- `.github/workflows/cleanboot.yml` already writes its own `sites/ci/site.sh` with `deis.py --new`
  and installs from it, "so the `--new` path stays tested". CI has never depended on the shipped
  establishment. It is the standing proof that from-nothing works.
- `scripts/deis.py --snapshot` keeps CESFAM, PSR, CECOSF, CGR, CGU, COSAM, SAPU, SAR and SUR, and
  the search matches any term against the row — `deis.py <tipo> <comuna>` works today. The CESFAM-only
  impression is created by the docstring's example, the README's *"Choose your CESFAM"*, and
  `provisioning/README.md`'s *"One stack serves one CESFAM"*. **No picker logic needs to change.**
- `themes/apsconecta/core/css/site.css` is generated by `15-branding.sh`, committed, and read by two
  things. `server.css` `@import`s it and already declares `var(--aps-clinic, "APS Conecta Gestión")`
  as the fallback. And the ADR-0001 asset guard in `scripts/test.sh` (lines 109–120) greps
  `/themes/apsconecta[^")]+` out of `server.css` and asserts each of the seven resulting paths exists
  on disk — the `@import` line matches that pattern, so **the guard requires `site.css` to exist**.
  The file's own header comment, that the committed copy "keeps `scripts/test.sh` green on a checkout
  that has never been seeded", is therefore accurate about the gate and only wrong about *which*
  establishment it names. Verified by running the guard's own pipeline: `site.css` is in its output.

Verified on the GitHub side, so it can be struck from scope: the `gestion` *About* description
already reads *"One establishment per install"*, the `APS-Conecta` org description and profile README
name no establishment, and a code search across all seven sibling repos returns zero hits. The only
GitHub surface carrying the name is the rendered `README.md`.

## Goals / Non-Goals

**Goals:**

- One rule that keeps holding, covering every per-install artifact rather than one exception granted
  per file: if its content depends on which establishment is installed, git does not track it.
- Installing leaves the working tree clean, so "the repo names no establishment" is a property that
  survives daily use instead of decaying the first time someone commits everything.
- The pilot install keeps running with no reconfiguration beyond preserving a file it already has.
- The from-nothing path is the documented path, and it is exercised on every CI run — which it
  already is.

**Non-Goals:**

- Changing the site file's format, location or contents. `sites/<slug>/site.sh` stays exactly what
  it is; only whether git tracks it changes.
- Changing what `deis.py` accepts or how provisioning consumes a site file.
- Rewriting the DEIS register or its selection rules.
- Purging the name from git history. It stays in past commits and that is correct — history records
  what was true. This change governs what a checkout of `main`, or of a tag, contains.
- Auditing `www.apsconecta.cl`. It is a separate repo (`aps-conecta-web`), it returned zero code-search
  hits, and its rendered pages are outside this change.

## Decisions

### Ignore `sites/*/` wholesale rather than deleting one directory

**Chosen:** add `sites/*/` to `.gitignore` and `git rm -r --cached sites/<slug>`, keeping the
register CSV tracked (it sits at `sites/*.csv`, so a directory-only pattern leaves it alone).

**Why over deleting just `sites/<slug>/`:** deleting one directory fixes today and leaves the
policy unwritten. The moment the pilot's file is reconstructed, or the first adopting clinic's file
lands in a branch, the same mistake is available again with nothing to stop it. An ignore rule is
the guard; a deletion is one instance of obeying it. It also puts a site file in the class it always
belonged to — install-local configuration, alongside `.env`, which is already ignored for the same
reason under a stronger threat model.

**Alternative rejected — keep `sites/<slug>/` tracked but relabel it "pilot fixture".** The
cheapest diff, and it fails the requirement: a clone would still contain a real, named, operating
establishment's team structure and access matrix. Relabelling changes how it reads, not what ships.

**Alternative rejected — ship a synthetic `sites/ejemplo/`.** Explicitly ruled out: the intended
first run is that an operator picks their own establishment from the register we supply. A synthetic
default is a fourth thing to maintain and an invitation to install the wrong one.

### `site.css` is untracked too — the same rule, not a second one

**Chosen:** gitignore `themes/apsconecta/core/css/site.css` and `git rm --cached` it. `15-branding.sh`
keeps writing it exactly as it does now. The ADR-0001 asset guard learns that one of its seven paths
is generated rather than static, and skips only that one, by name, with the reason in a comment.

**Why:** its content is a pure function of which establishment is installed — the same property that
makes a site file install-local. Two artifacts of one kind should obey one rule. Untracking also
removes the failure mode below rather than guarding it.

**Alternative rejected — commit the file with a neutral `"APS Conecta Gestión"` value.** This was the
earlier choice here, made on the incorrect belief that nothing in the gate read the file. It creates
a defect the tracked-neutral form cannot escape: the committed value is neutral, every install writes
the real establishment's name, so **the tree is permanently dirty on a tracked file whose diff is the
clinic's name**. `git commit -a` then re-publishes precisely what this change removes, and the noise
is permanent, so it stops being read. A pre-commit hook was considered to block that commit and
rejected as a guard bolted onto the defect: nothing needs guarding once the file is not tracked.

**Why the fresh-checkout case is safe:** a failed `@import` is ignored by CSS and affects no other
rule, so the interface renders `var(--aps-clinic, "APS Conecta Gestión")` — the product's own name.
The window is a checkout that has never been provisioned, and provisioning precedes any use of the
instance. The repo therefore reads as agnostic because of what the code does, not because someone
kept a committed string neutral.

**Trade-off:** the asset guard goes from "every referenced path exists" to "every referenced *static*
path exists". That is a narrowing, and it is stated in the guard's comment so the next reader sees a
decision rather than an oversight. It shipped for months declaring four `.woff2` files that never
existed (ADR-0001), so the guard earns its strictness — the exclusion is one named path, not a
pattern that could swallow a future asset.

The file's header comment is rewritten rather than deleted: the gate really does depend on it, so the
replacement says the file is generated per install, is not tracked, and is skipped by name in the
asset guard.

### `docs/adr/0005` is not edited

Its Context cites `sites/<slug>/site.sh` setting `SITE_DOMINIO=""` as measured evidence for
"gestion is not production". That was true when the decision was taken. An ADR is a dated record;
rewriting its evidence to match a later repo makes the record useless. If a documentation audit
later flags the path as an orphan reference, the fix is a dated superseding note, not a rewrite.

### Vocabulary: "establecimiento de atención primaria", CESFAM as one type

The product-level noun becomes *establishment* (English docs) / *establecimiento* (Spanish, staff-
facing), matching the wording the GitHub description and `AGENTS.md` already use. CESFAM stays
everywhere it is genuinely specific — the shared role registry is written around a CESFAM's
positions, and `deis.py`'s generated comment *"the 22 every CESFAM has"* is accurate about that
registry. This is a copy edit with a boundary, not a find-and-replace: replacing every "CESFAM"
would make true statements false.

## Risks / Trade-offs

- **A `git pull` deletes the pilot's site file from a working tree that has it** → the highest-cost
  risk here, and it is silent. Mitigated by ordering: the operator copies `sites/<slug>/` out
  of the tree *before* the change lands, restores it afterwards (it is then ignored and stays put),
  and the removal is announced in `CHANGELOG.md` rather than discovered. One developer holds the
  only affected copy today, which makes this cheap — and makes it easy to forget.
- **A site file no longer gets code review** → real and accepted. An ACL matrix is exactly the kind
  of thing review catches. Countervailing: `make install` refuses to run against a malformed site
  file, `make divergence` reports what is live but undeclared, and `scripts/test.sh` still lints any
  `sites/*/site.sh` present in the tree. The pilot's file can be held wherever the install host's
  configuration is held; this repo is not the right place for one clinic's data.
- **The lint sweep silently covers nothing** → `scripts/test.sh` lints `sites/*/site.sh` and, with
  nothing tracked, a bare clone lints zero site files. The tracked-file subset check stays green
  because both sides lose the entry, so the gate does not go red — it goes *quiet*, which is the
  failure mode its own comment warns about. Confirm by running the gate on a clean clone, not by
  reasoning about it.
- **The asset guard's exclusion grows into a hole** → it must skip `site.css` by exact name, never by
  a `*.css` or directory pattern. A pattern would silently stop checking assets added later, which is
  the same class of bug ADR-0001 was written for. Assert the guard still fails when a *static* asset
  is removed, rather than trusting that it does.
- **"Verify from a clean clone" cannot mean a second stack on one host** → `compose.yaml` line 9 pins
  `name: apsconecta-gestion`, so every checkout on a machine resolves to the SAME compose project,
  the same containers and the same volumes. A second clone with different `HTTP_PORT`/`OFFICE_PORT`
  does not isolate anything: it recreates the running stack on new ports and provisions its own site
  file over whatever was installed. Learned the hard way during this change — a probe clone
  provisioned a PSR onto the live pilot instance, and the tell was the divergence
  report listing the pilot's own sectors as undeclared. A clean-clone check must therefore either run
  `docker compose down -v` first and own the host's single stack, or stay a *static* check on the
  archived tree (`git archive` + `make install` refusing before it starts anything), which needs no
  containers at all. Nothing here is a defect in the fixed project name: one host runs one
  establishment, which is the product model.
- **A generated file's absence is invisible until someone looks at the header** → accepted. The
  window is a checkout that has never been provisioned; the fallback renders the product name, which
  is a correct thing to show, not a broken one. There is no state in which a wrong establishment
  renders.
- **Nobody can run the suite straight from a clone** → intended. The cost is one `deis.py` invocation
  before the first `make install`; the benefit is that nobody installs someone else's clinic by
  accident.

## Migration Plan

1. Preserve the pilot's `sites/<slug>/` outside the working tree before the change lands. Only
   the site file needs preserving — `site.css` is rewritten by the next install and holds nothing an
   operator authored.
2. Land the change: untrack both per-install artifacts, ignore them, teach the asset guard, re-word.
3. Restore the preserved directory into `sites/<slug>/`. It is now ignored; `SITE=<slug>`
   keeps working and `make install` converges as before, this time leaving the tree clean.
4. Verify from the other side: a fresh clone into a scratch directory, `make setup`, then
   `make install` — it must stop and name the picker.

**Rollback:** revert the commit. Both files return to tracking from git history, and a working copy
that kept its local site file sees no change. There is no data migration to undo.
