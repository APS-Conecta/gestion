# Institutional mail: verified integration boundaries

Research date: 2026-10-30. This is a separate future plan. It changes neither master plan #175 nor the current #188 implementation. Sources are official documentation and pinned upstream code; no mail server was installed or contacted with credentials.

## Confirmed product decisions

- One dedicated mail VM per establishment, on the same physical server as APS; both services use one static public IP through a validated shared ingress. Nextcloud Mail is the staff-facing mail interface; SMTP delivery and technical management remain backend services.
- The installer accepts the establishment's controlled email domain and preserves APS Nextcloud 34 as the application instance.
- Personal primary addresses include given name(s), both surnames and the selected role. Example: `ana.maria.rojas.fuentes.enfermeria@center.example.org`.
- Collisions receive a persisted numeric suffix, with administrator preview and a validated correction option. Reinstalling preserves existing allocations.
- The existing roster has one combined `apellidos` field and permits several role groups. The mail plan needs explicit surname fields and a selected mail role; it must not guess compound surnames or break the current six-column template.
- Prove shared HTTPS/ACME/mail routing, restricted VM administration and the credential bridge before implementation. This research authorizes no deployment.

## Supported interfaces and credential limits

**MIAB management:** HTTPS endpoints under `/admin` list users/domains/aliases; create users; change passwords and quotas; remove users; and create/update/remove aliases. A domain is inferred from an address, rather than created through a separate mail-domain POST. Alias fields include `address`, `forwards_to`, `permitted_senders` and `update_if_exists=1`. User creation rejects duplicates rather than reconciling them. Query before creating; never rotate a password on an ordinary retry. [v77 routes](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/daemon.py), [validation and mutation](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/mailconfig.py).

The published OpenAPI page identifies itself as 0.51.0; v77 implementation is the version authority. Authentication supports Basic credentials with MFA when configured, a login session key, or the machine's system API key. The checked management endpoints require administrator authority across the box; no per-establishment scope was found. Sessions are memory-resident, expire after two days of inactivity, and depend on password/MFA state. A session token is not a permanent integration credential. [API documentation](https://mailinabox.email/api-docs.html), [authentication source](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/auth.py).

Use an HTTPS client library with verified TLS, in-memory authorization and request bodies. Feed initial secrets through a private descriptor/stdin or an explicitly managed secret store; redact failures. Do not reproduce documentation's password-bearing curl arguments. **Boundary caveat:** upstream MIAB itself invokes `doveadm pw -p <password>` when hashing a new/reset password and when authenticating an administrator by password. Thus client-side secret-safe HTTP does **not** satisfy an absolute end-to-end prohibition on plaintext in process arguments. That strict requirement needs an upstream-supported correction or an explicitly accepted boundary; bypassing MIAB with SQLite writes is not a solution. [Hashing code](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/mailconfig.py), [authentication code](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/auth.py).

**Nextcloud Mail provisioning:** its native administrator configuration creates client accounts using domain matching and `%USERID%`/`%EMAIL%` templates; LDAP placeholders require an actual LDAP backend. There are no native name/surname/role placeholders for APS local accounts. Resolve the institutional address in the installer, preserve that mapping, then use the resolved profile email or UID. Admin UI routes support configuration and bulk provisioning, but are internal, authenticated, CSRF-protected app routes rather than a documented stable OCS account-creation API. [Templates](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Db/Provisioning.php), [settings controller](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Controller/SettingsController.php), [routes](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/appinfo/routes.php).

Native provisioning obtains the Nextcloud login password while the user accesses Mail and encrypts it through `ICrypto` into the client account. It does not create or update the MIAB mailbox password. Therefore zero-setup login requires aligned credentials and an explicit future synchronization policy; Nextcloud password changes, passwordless/SSO login and app-password login must be tested. Master-user mode assumes corresponding server support; MIAB's checked Dovecot setup configures SQL user passwords, not master-user authentication. Do not introduce a shared password for all mailboxes. [Provisioning manager](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Service/Provisioning/Manager.php), [credential middleware](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Http/Middleware/ProvisioningMiddleware.php), [MIAB authentication setup](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/setup/mail-users.sh).

For distinct mailbox credentials, Mail's existing user-facing account-creation route accepts secrets in an authenticated HTTPS request body and encrypts them through its setup service; it acts as the current user, not as an administrator choosing another UID. This is a version-pinned internal integration candidate requiring a session/CSRF proof. The registered `mail:account:create-imap` and update commands accept passwords in argv, with no stdin/environment secret option in the inspected version. A descriptor-fed, in-process invocation of the existing command is only a possible proof spike, not a verified supported interface. No direct account-table or manually encrypted database writes should be planned. [Account controller](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Controller/AccountsController.php), [create command](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Command/CreateImapAccount.php), [update command](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Command/UpdateImapAccount.php).

## Infrastructure, identity and operations

- Public mail requires a controlled domain, stable public addressing, correct forward/reverse DNS and usable SMTP port 25 in both directions. PTR belongs to the hosting provider. MIAB can manage authoritative DNS or expose records for external DNS; validate MX, SPF, DKIM and DMARC before declaring delivery ready. HTTPS and mail certificates must validate for the chosen mail hostname. [Guide](https://mailinabox.email/guide.html), [v77 status checks](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/status_checks.py).
- A suitable client profile is IMAPS 993 plus authenticated SMTPS 465, or submission 587 with mandatory STARTTLS. MIAB also owns web, DNS and Sieve services. Its actual firewall includes 587 although the guide's short port list omits it. Keep Mail TLS peer verification enabled. Private-address mail hosts require review of Nextcloud's local-remote-server restriction. [SMTP setup](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/setup/mail-postfix.sh), [IMAP setup](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/setup/mail-dovecot.sh), [NC34 administrator documentation source](https://github.com/nextcloud/documentation/blob/stable34/admin_manual/groupware/mail.rst).
- MIAB mailbox names accept lowercase ASCII letters, digits, `.`, `_` and `-`; complete addresses are unique. APS must define accent/transliteration rules, collisions, center namespace and renames. **Proposed design:** bind a resolved address permanently to establishment + immutable staff identity; reject occupied addresses and never silently adopt another person's mailbox. [Validation and database schema](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/mailconfig.py), [unique constraints](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/setup/mail-users.sh).
- A role address can forward to a person's mailbox and authorize that person to send as the role through `permitted_senders`. This does not create a shared historical mailbox or move old messages to a successor. Handovers require decisions about history, sent-mail ownership and revocation. Mail 5.12.6 refuses native delegation of provisioned accounts; do not promise that feature without a dedicated proof. [MIAB aliases](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/mailconfig.py), [sender validation](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/setup/mail-users.sh), [Mail delegation guard](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Controller/DelegationController.php).
- Nextcloud user deletion removes its Mail client records; no MIAB account lifecycle is called. MIAB removal deletes the login row but leaves mailbox files visible as inactive storage. Disable, retain, transfer and erase are separate explicit operations; neither API alone defines institutional retention. [Nextcloud deletion listener](https://github.com/nextcloud/mail/blob/4382f766dd38b7d6102589df1231c47af85a02b9/lib/Listener/UserDeletedListener.php), [MIAB removal/archive behavior](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/mailconfig.py).
- MIAB backups are encrypted Duplicity backups of its storage root; the recovery key must be stored separately. Backups stop mail services. Restoration to a new box requires an appropriately updated source, restore, setup rerun and DNS cutover. APS Borg backup does not cover this separate host automatically; test both restorations and client reauthentication. [Backup implementation](https://github.com/mail-in-a-box/mailinabox/blob/df7f245e0e54e7b5292837504422a97999ee33f3/management/backup.py), [maintenance/recovery](https://mailinabox.email/maintenance.html).

## Unresolved decisions and proof spikes

1. Prove the confirmed same-physical-server, dedicated-VM-per-center deployment. Prove the confirmed one-static-IP shared ingress and record domain/DNS ownership. Confirm provider PTR control and unblocked port 25 before provisioning users.
2. Implement the confirmed given-name + both-surnames + role naming rule and stable numeric collision suffixes. Settle permanent cargo-account mailboxes, rename preservation, leaver access, handover history and retention. Bind ownership to immutable identity, not mutable names.
3. Choose an authentication model. Prove native aligned-password provisioning, or prove the version-pinned authenticated account route for independent credentials. Confirm secret handling on **both** hosts; resolve MIAB's internal argv behavior before claiming the strict guarantee.
4. On disposable hosts with synthetic users only, prove interrupted creation/retry, preexisting-address refusal, per-center isolation, TLS failure, password rotation, disabled-user access, role send-as revocation and active-session behavior. A successful API POST is not mail acceptance.
5. Prove external inbound/outbound delivery with DNS authentication and a fresh Mail login on APS Nextcloud 34; restore mail data and the APS client configuration from separate backups. Use the suite manifest, acquisition/lock rules and existing installation/revalidation seams; no production integration has been implemented by this research.
